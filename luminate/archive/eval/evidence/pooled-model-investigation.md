# Follow-up: could Wellms run on a POOLED tenancy model (single DB, `TenantId` discriminator)?
Date 2026-10-08. Same build as the main report (API commit `3dd34ebe`, Laravel 9.52.21, PHP 8.3, Postgres 12). Labels: **[V]** Verified (I ran it), **[D]** Documented (source/docs read, not run), **[U]** Unknown. Estimates are marked as estimates.
Scripts: `scripts/p01..p21*`; add-on spike: `custom/pooled-spike/`; raw outputs: `evidence/p0*.txt`, `p1*.txt`, `p2*.txt`.

## 0. How I tested
Two new domains (`pooled-c.localhost`, `pooled-d.localhost`) added **at runtime** with `php artisan domain:add`, both pointed at ONE database `pooled` (migrated once, 151 base tables), one bucket, one Redis DB, one shared Passport key pair. Tenant C got confidential data (course, lesson, topic, quiz, a student with a quiz attempt); tenant D got its own admin and course. Every probe is "tenant D, with its own valid admin token, tries to read, write or link tenant C's data". The add-on (`luminate/wellms-pooled-spike`) is a Composer package installed beside Wellms; **no Wellms code was patched**.

## 1. Feasibility
- **Shared DB with laravel-multidomain: [V] trivial.** The DB binding is plain environment data: `DB_DATABASE=pooled` in each domain's `.env.<domain>` file. Two domains, one DB, one `migrate` run. DB switching is not load-bearing in code; what *is* load-bearing is that `DetectDomain` swaps the **entire environment file** per request (DB, Redis, S3 bucket/URL, app key, app name) [D, source `Foundation/Application.php`; consistent with behaviour].
- **Baseline with no tenant logic [V]: total leakage.** D listed C's course and users, C's token was accepted on D (shared keys + shared `users`), and D **deleted** C's course (HTTP 200). All the work is the discriminator.
- **Hot tenant add [V]:** `domain:add` + `domain:update_env` work without restarting the container. Caveat [V]: the queue-worker and scheduler loops use a static `MULTI_DOMAINS` list (and generated supervisor files), so a hot-added tenant gets web traffic but **no background jobs until restart**.
- **Real paths I built and tested [V]:** (a) Laravel global scopes registered from an add-on package (`Model::addGlobalScope` + `creating` stamping, no core patch); (b) **PostgreSQL Row-Level Security** with `tenant_id` defaulting from a session setting; (c) tenant-aware cache prefix; (d) tenant-tagged queue payloads; (e) S3 key prefix via Laravel's `root` option; (f) a DDL event trigger for new tables.
- **`stancl/tenancy` (single-DB mode) and `spatie/laravel-multitenancy`: [U] not evaluated here.** From general knowledge they solve the same per-model scoping and job-context problems I solved by hand; neither would cover raw SQL, `exists:`/`unique:` validation, or the query cache, which are what the RLS layer closed. Treat as untested.

## 2. Data model
- **Counts [V]:** 151 base tables = 106 Wellms application tables + 24 TRAX (xAPI) + 8 H5P + 5 Passport + 5 Spatie roles/permissions + 3 Laravel framework. **142 concrete Eloquent model classes over 105 tables**; 46 tables have no model class (pivots such as `course_user`, `course_group`, `group_user`, `course_author`; TRAX; Passport). `evidence/p07_models_by_table.*`, `p02_schema.txt`.
- **No existing tenant/owner discriminator [V]** (only per-row `user_id`/`author_id`/`created_by` ownership; TRAX has its own `owner_id` model). **No existing global scopes [V]:** `addGlobalScope`/`withoutGlobalScope` occur 0 times in Wellms packages; only `SoftDeletes` in the auth package. So there is nothing to conflict with, and nothing to build on.
- **Scopes are per exact class, and Wellms duplicates model classes over the same table [V]:** 16 tables are queried by more than one class: `users` by **16** (every package ships its own `User`), `courses` by 5, `categories` 4, `groups` 3, `consultations` 3, `lessons`/`carts`/`orders`/`products`/`cart_items`/`order_items`/`dictionaries` 2 each. Proved live: a scope on `EscolaLms\Courses\Models\Course` did not protect `EscolaLms\CourseAccess\Models\Course` (D read C's **course access list**, listing C's student, while `GET /courses/{id}` correctly returned 404).
- **Query paths that bypass an Eloquent global scope [V, census over 50 packages + app code]:** 95 `DB::` facade uses (35 `DB::raw/select/table/...`), 35 raw SQL fragments (`whereRaw`, `selectRaw`, ...), 84 query-builder joins/sub-selects, **152 `exists:`/`unique:` validation rules** (Laravel's presence verifier uses `DB::table`), 129 export/import sites (Maatwebsite), 42 `getConnection()/getPdo()` uses, 28 uses of the Eloquent **query cache**, 14 `Cache::` sites. `evidence/p03_source_census.txt`.
- **Riskiest by name [V from census, bold = shown to leak in my tests]:** `reports` (DB::raw 10, joins 39, raw 12; **`TutorsPopularityMetric` leaked tenant C's admin to D under model-scope-only**), `questionnaire` (DB 10, joins 16), `courses` (`ProgressService` raw `leftJoinSub` over `course_user`/`course_group`; `Course.php`), `recommender` (`TermAnalyticService` raw), `headless-h5p` (repositories, `QueryExtendable`), `cart` (`ProductService`, `ShopService`), `webinar` criteria, **`course-access` (second Course class)**, **`topic-types`/`topic-type-gift` (query-cached `AbstractTopicContent`)**, and all validation rules (**`access/add` accepted a foreign user id**).
- **Natural-key unique indexes that collide across tenants [V]:** 24, e.g. `users(email)`, `coupons(code)`, `trax_users(email,username)`, `trax_owners(name)`, `questionnaire_model_types(model_class)`, `hh5p_contents(nonce)`. `users.email` shown live: with a global unique index, D creating a user with C's email returned a raw SQL error that **echoed C's email** (existence oracle); replaced by `unique(tenant_id,email)` and D then created its own user with that email (201) [V].

## 3. Isolation integrity: how sure can we be?
Layers tested, with the same probe matrix (17 read probes, plus writes, validation, auth), from D against C's data:

| Configuration | Read probes leaking (of 17) | What still got through |
|---|---|---|
| Nothing (shared DB) | all | everything, including delete [V] |
| Eloquent scopes on 5 core classes (partial) | 4 | unscoped quiz/attempt tables leak whole; access list via second Course class; foreign user linked by `exists:` rule [V] |
| Eloquent scopes on every class of 10 tables (33 classes) | 0 | **foreign link via `exists:` validation created a cross-tenant pivot row** (`course_user(user 2 of C, course 3 of D)`), C's course list then contained D's course id; `TutorsPopularityMetric` showed C's admin to D; roles and config shared; **console/queue fail open** (`Course::count()` = 2 across tenants) [V] |
| **RLS only** (no Eloquent scopes) | 1 (see next row) | closed the `exists:` link (422), the report leak, the access list, pivots, raw SQL; **but query cache served C's cached row to D and poisoned the owner** [V] |
| **RLS + per-tenant cache prefix + queue tagging** | **0** | write/validation probes rejected (422/404/403); C's token on D = 401; remaining: roles/config/translations tables not under RLS in the spike (shared, [V]) |

Where the gaps are, as asked:
- **Reports [V]:** raw joins escape model scopes; RLS closed them.
- **Exports [U]:** two export probes returned 500/422 (empty sheet), so they were not conclusive; they are DB-bound and should fall under RLS [D].
- **Admin endpoints [V]:** endpoints using a second model class (course access) leaked under scope-only; fine under RLS.
- **Queued jobs [V]:** untagged jobs in one shared worker ran with no tenant: under RLS they saw 0 courses/0 users (silent no-op, **fail closed**); under scope-only they see everything (**fail open**). With tenant tagging each job restored its tenant (C's job saw 1 course/2 users, D's 1/1) through ONE worker.
- **Cached data [V]:** the Eloquent query cache keys on SQL text; with RLS the SQL is unchanged, so tenants share cache entries (leak and poisoning). A per-tenant cache prefix fixed all three read orders. Under Eloquent scopes the tenant is in the SQL binding, so keys differ. `AdministrableConfigService::CACHE_KEY` is a constant [D, source]: shared settings cache.
- **Full-text search [D]:** only `ilike` on tables (34 sites), no external search engine found; DB-bound, covered by RLS.
- **File paths [V/D]:** ids come from one sequence so keys cannot collide; a per-tenant prefix works via the S3 `root` option (below). Anyone holding bucket credentials still sees all tenants.
- **Auth [V]:** with a shared key pair the JWT is not tenant-bound (baseline: C's token worked on D). Isolation then depends entirely on the tenant-scoped user lookup. **Pitfall found the hard way:** my first add-on discovered model classes by instantiating them (`new $class()`), which booted models and resolved the authenticated user *before* the scopes existed; the guard memoised an unscoped user and C's token authenticated on D. Fixed by `newInstanceWithoutConstructor()` (C's token then 401). Lesson: scope registration must be the first thing that happens, and any step that can touch auth before it fails open.
- **Confidence statement.** After RLS + cache prefix + queue tagging I could not make any DB-bound probe leak, including the raw-SQL, validation and report paths that defeated model scopes. That is stronger than any model-scope design could be, but it is **not proof**: the probes covered 14 tables under RLS, not all 105 model tables, and 17 reads plus a few writes, not all 439 operations. The state outside Postgres (14 `Cache::` sites, files, TRAX, Horizon, anything keyed without a tenant) needs its own review [U].

## 4. Cross-cutting changes under a pooled model

| Concern | Siloed (native) | Pooled (what I tested) |
|---|---|---|
| Database | DB per tenant; `migrate` per tenant | one DB; `migrate` **once** [V] (151 tables); add-on migration adds `tenant_id`; new Wellms tables on upgrade handled by a Postgres DDL **event trigger** that adds `tenant_id` + forced RLS + policy automatically [V] |
| Isolation mechanism | by construction (separate DB + role) | RLS policy `tenant_id = current_setting('app.tenant_id')`; write path stamped by column default from the same setting (covers Eloquent, `DB::table`, raw, pivots) [V] |
| Postgres role | any | **must not be superuser/BYPASSRLS**: the stock compose connects as `default`, a superuser, which bypasses RLS entirely [V]; migrations need a separate owner role [D] |
| Connection model | n/a | I used a session-level setting on non-persistent php-fpm connections [V]. With PgBouncer transaction pooling a session setting would leak across tenants; needs `SET LOCAL` per transaction [D, not tested] |
| Files | bucket per tenant | one bucket + prefix: `config(['filesystems.disks.s3.root' => 'tenants/<id>'])` per request; `put/get/url` all followed the prefix (`pooled/tenants/pooled-c.localhost/course/5/...`) [V via Storage facade; Wellms' 218 `Storage::`/`disk()` call sites use the same disk, not individually tested] |
| Redis / queue | `REDIS_DB` per tenant (needed to stop cross-tenant job execution, see main report) | one Redis DB; **tenant id stamped into every job payload** with `Queue::createPayloadUsing`, restored in `JobProcessing` [V]; Wellms' own queued listeners go through the same path [D] |
| Auth keys | key pair per tenant | one key pair worked [V]; the token is not tenant-bound, so add a `tenant` claim check at the proxy [U]; per-tenant keys remain possible because key files are per-domain storage [D] |
| Cache | prefix derived from per-tenant `APP_NAME` | must set a tenant-specific prefix per request (query cache, constant-key settings cache) [V] |
| Roles, settings, config, translations | per tenant (per DB) | **shared** unless moved under RLS: C narrowed the `student` role and changed a config value, D saw both [V]. Spatie roles/permissions per tenant may need its teams feature or patches [U] |
| Scheduler / console | per-domain loop | console has no tenant: fail open (scopes) or closed (RLS); needs a per-tenant loop [D] |
| xAPI (TRAX, 24 tables) | per tenant | has its own owner/access model; mapping tenant to owner not tested [U] |
| Offboarding / per-tenant restore | drop DB, delete bucket | `DELETE ... WHERE tenant_id` over ~106 tables plus prefix delete; per-tenant restore is hard [D] |

## 5. Effort and maintenance
- **Silo provisioning cost, measured [V]:** a fresh siloed tenant provisioned **hot in 24 s with no restart** (role+DB 1 s, bucket 1 s, domain+env 3 s, migrate 7 s, keys 3 s, seed 11 s), 15 MB on disk, served immediately, admin could log in. Caveats: static worker/scheduler list needs a restart; values with spaces must be quoted or the tenant is half-built (hit twice).
- **What required patching Wellms core: nothing in what I tested [V].** Tenant resolution, scopes, RLS, cache prefix, queue tagging, S3 prefix, composite uniques and the event trigger are all package/SQL/config. **Likely needs patching or wrapping [U]:** per-tenant roles/permissions, per-tenant settings/config/translations if they must differ per tenant, TRAX owner mapping, any code that uses a second DB connection or a raw connection without the session setting.
- **Sizing (my estimates, not measurements):**
  - Spike built here: about one working day; it registered **33 of 142 model classes (23%)** and put **14 of 151 tables** under RLS, but exercised every mechanism.
  - Production-grade pooled add-on: **L**, roughly 2 to 4 engineer-months for a first version: tenant resolution from JWT/host, RLS on all tenant-owned tables + event trigger, role split (app vs migration owner), cache/queue/storage hooks, tenant-scoped roles/settings/config, composite uniques (24 natural keys to decide), TRAX decision, per-tenant scheduler loop, offboarding tooling, runbooks, and an **auto-generated cross-tenant test over all 439 OpenAPI operations as the release gate**.
  - Siloed with automation: **M**, roughly 2 to 4 weeks: IaC for DB/role/bucket/keys/env, a dynamic tenant registry replacing the static `MULTI_DOMAINS` loop, per-tenant `REDIS_DB` (or Redis per tenant group) and cache prefix defaults, per-tenant S3 keys, host allow-list, offboarding scripts.
- **Ongoing tax, pooled:** a permanent audit surface of 142 classes, 151 tables and about 400 raw-query/validation/cache sites that Wellms changes without knowing about your isolation. Per Wellms release: run the isolation suite and review the schema diff (the event trigger auto-protects new tables, but not new shared/global tables or new unique indexes): **S, about 1 to 3 days**. At Laravel or major module upgrades (already required, see main report): **M, about 1 to 3 extra weeks** to re-prove isolation. Add-on survives upgrades only as long as Wellms keeps the same extension points; no fork to re-apply for what was tested.
- **Ongoing tax, siloed:** near zero code tax. Ops tax scales with N: each upgrade's migrations run N times (about 7 s each on an empty DB, so about 2 hours serial for 1,000 tenants, an estimate), N databases to back up and monitor, a worker loop that scans every tenant.

## 6. Verdict: (b) feasible, but not worth it as the default
- **Feasible: yes, more than I expected.** Postgres RLS plus three small hooks (cache prefix, job tagging, S3 root) closed every DB-bound leak I could construct, from an add-on with no core patch, and an event trigger keeps future tables protected.
- **Not worth it now:** it trades Wellms' strongest verified property (isolation by construction, main-report objective 2) for an isolation guarantee that you must **re-prove on every upgrade** across code you do not control (about 400 vendor query sites, 14 cache sites, 142 model classes with duplicated tables) and that fails open or silently when any piece is missed (a console job, a cache key, a bypass role, a pooled connection). The first add-on I wrote **leaked through its own boot order**; that is the realistic failure mode. Wellms' tenant-specific state (roles, settings, config, translations, TRAX, cache prefix by app name) was designed for per-tenant environments, so pooling means converting each to DB-backed per-tenant state.
- **Middle ground (recommended): keep Wellms siloed and make per-tenant cost pure ops.** Automate provisioning (24 s hot today), replace the static `MULTI_DOMAINS` loop with a registry-driven worker/scheduler, give each tenant its own `REDIS_DB` (or Redis group), cache prefix, S3 keys and JWT keys, add a host allow-list, run Wellms as a non-superuser role, and let Luminate's .NET layer own the tenant registry so that "adding a tenant = inserting a row in Luminate" still holds on your side while the provisioner does the work behind it. If tenant counts later reach thousands of small tenants, introduce the RLS pooled add-on **only for that small-tenant tier**, behind the same registry, using this spike as the starting point.

### Recommendation paragraph for the architecture report
> We investigated running Wellms on our pooled tenancy model (one database, a `tenant_id` discriminator, tenant resolved per request) against a live instance and the source. It is **feasible without forking Wellms**: pointing many domains at one database needs only configuration, and a spike package plus PostgreSQL Row-Level Security (tenant stamped by a column default from a session setting), a per-tenant cache prefix, tenant-tagged queue payloads and an S3 key prefix produced no cross-tenant leak in our probes, with a DDL event trigger protecting tables added by future upgrades. It is also **not worth adopting as the default**: Wellms ships no tenant column and no global scope, has 142 model classes over 105 tables (16 tables are mapped by several classes, `users` by sixteen), and roughly 400 raw-SQL, join, validation and cache sites that Eloquent scopes cannot reach, so isolation would rest on a database-layer guard that we must re-prove on every upgrade and that fails open or silently when any piece is missed (our own first add-on leaked through its boot order, a console job, a query-cache hit and a superuser connection each leaked or no-opped until fixed). Roles, settings, config and cache keys also assume per-tenant environments and would need converting to per-tenant database state. Our recommendation is to keep Wellms **siloed and automate provisioning**, which we measured at 24 seconds, no restart and 15 MB per tenant, replace its static worker/scheduler tenant list with a registry driven by Luminate, give each tenant its own Redis DB, cache prefix and storage keys, and run Wellms as a non-superuser database role; the RLS pooled add-on remains a validated option for a future tier of many small tenants, sized at roughly two to four engineer-months plus a standing isolation test suite.

## 8. Mistakes and artefacts to be aware of
- My first spike showed "C's token accepted on D": a bug in the spike's class discovery (boots models before scopes), found with SQL logging, fixed, retested (401). Not a Wellms behaviour.
- My probes deliberately narrowed the shared `student` role in the pooled DB (to show roles are global); later runs reflect that. Restored from the default tenant before the queue test.
- The "LEAK carol@c.test" flag on the final run is a false positive of my marker test: D legitimately created its own user with that email.
- A command containing a file removal inside a `sh -c` script was blocked by the environment's safety check; I did not retry it in another form and instead used append-only logs.
- Left running in the environment: databases `pooled`, `tenant_e` (half-built by a quoting error), `tenant_f`; buckets `pooled`, `tenant-e`, `tenant-f`; domains `pooled-c/d`, `tenant-e/f`; the spike package and RLS objects in `pooled`; all inside the throwaway Docker stack.
